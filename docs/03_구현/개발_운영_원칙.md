# 개발 운영 원칙

## 작업과 배포

- `main`은 Production, `feature/*`는 작업, `preview`는 고정 Preview 주소를 위한 배포 포인터로 사용한다.
- 작업·PR·merge는 피처 브랜치에서 진행하고 `preview`에서는 직접 작업하지 않는다.
- 원격 화면 검증이 필요하면 피처 브랜치 HEAD를 `preview`에 게시한다.
- Production 검증 후 `preview`를 최신 `main`으로 돌린다.
- 일반 기능은 원격 Preview에서 검증하며 로컬 서버나 로컬 DB를 필수로 사용하지 않는다.

## Supabase

- Preview와 Production은 하나의 Supabase 프로젝트를 공유한다.
- Preview는 관리자 권한이 없는 일반 테스트 사용자를 사용하고 전용 조건 분기를 실코드에 추가하지 않는다.
- Preview 전에는 새 테이블·nullable 컬럼·새 함수처럼 기존 Production과 호환되는 변경만 적용한다.
- RPC 계약을 바꾸면 새 버전 함수를 추가하고, 삭제·대규모 변환은 별도 승인 후 진행한다.
- 테스트 데이터는 실코드 예외 처리 대신 테스트 계정 초기화로 정리한다.

## 릴리스

1. 구현 단계에서 빌드와 DB 이력을 검증하고, 필요하면 고정 Preview를 확인한다.
2. 사용자 승인 후 버전, `version.json`, 패치노트 migration을 작성하고 PR을 merge한다.
3. Production의 `/`, 인증 경로, `/version.json`을 확인한다.
4. Production 성공 후 패치노트 migration을 적용하고 DB 이력을 최종 확인한다.

버전 기준은 `app/package.json`이며 `app/public/version.json`과 패치노트에 같은 버전을 사용한다. Production 성공 전에는 패치노트를 원격 DB에 공개하지 않는다.

## 필수 설정

- Vercel Root Directory: `app`
- Build Command: `npm run build`
- Output Directory: `dist`
- Supabase Auth Redirect URLs: Production과 고정 Preview의 필요 경로

## 기본 원칙

- 이미 적용된 migration은 수정하지 않고 새 migration을 추가한다.
- 전투, 보상, 재화, 인벤토리, 랭킹은 서버가 확정한다.
- 앱 문구는 짧고 기능적인 터미널 판타지 RPG 스타일을 유지한다.
