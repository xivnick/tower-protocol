# 개발 운영 원칙

## 브랜치와 배포

- `main` 브랜치는 production 배포 기준으로 사용한다.
- 기능 작업은 `feature/*` 브랜치에서 진행한다.
- `preview` 브랜치는 사용자가 항상 같은 주소에서 검증할 수 있게 현재 검증 대상 커밋을 가리키는 배포 포인터로 사용한다.
- `preview`에서는 직접 개발하거나 커밋하지 않으며, PR의 base나 production 머지 대상으로 사용하지 않는다.
- 하나의 기능만 고정 Preview 검증 대상으로 게시한다. 다른 피처 브랜치의 자동 Preview 주소는 보조 진단용으로만 사용한다.
- 고정 Vercel Preview를 확인한 뒤 피처 브랜치를 `main`에 merge한다.
- 작업 단위가 끝나면 하나의 의미 있는 커밋으로 남긴다.
- PR merge 후 완료된 remote/local feature 브랜치는 삭제한다.
- `preview` 브랜치는 삭제하지 않고 Production 배포 후 최신 `main`을 가리키도록 되돌린다.

### 고정 Preview 흐름

```txt
main             -> Production
feature/*        -> 실제 작업, 커밋, PR
preview          -> 현재 검증할 feature HEAD, 고정 Preview 주소
```

1. 최신 `main`에서 `feature/*` 브랜치를 만든다.
2. 구현과 검증 후 피처 브랜치에 커밋하고 원격으로 푸시한다.
3. 같은 커밋을 원격 `preview` 브랜치에 게시한다.
4. Vercel의 `preview` 브랜치 전용 고정 주소에서 기능을 검증한다.
5. 사용자 확인 후 피처 브랜치에서 `main`으로 PR을 생성하고 merge한다.
6. Production 배포와 스모크 검증을 마친 뒤 `preview`를 최신 `main`으로 다시 맞춘다.

`preview`는 여러 피처의 통합 브랜치가 아니라 교체 가능한 배포 포인터다. 갱신이 필요하면 정확한 원격 대상을 확인한 뒤 `preview`에만 `--force-with-lease`를 사용할 수 있다. `main`과 피처 브랜치에는 강제 푸시하지 않는다.

### 역할 분담

Codex가 처리하는 작업:

- 최신 `main` 확인, 피처 브랜치 생성, 구현과 검증
- 호환 가능한 Supabase migration 작성·원격 적용과 DB 이력 확인
- 빌드와 DB lint, 커밋과 피처 브랜치 푸시
- 원격 `preview` 생성·갱신과 고정 Preview 주소 안내
- 사용자 머지 확인 후 버전·패치노트 파일 작성, PR 생성과 merge
- Production 배포 상태와 기본 경로 확인
- Production 성공 후 패치노트 migration 적용·공개
- 완료된 피처 브랜치 삭제와 `preview`의 최신 `main` 동기화

사용자가 처리하는 작업:

- 최초 1회 Vercel Git 연결·환경 변수·Deployment Protection 확인
- 최초 1회 `preview` 브랜치 주소 확인 또는 선택 사항인 Preview 전용 도메인 연결
- Supabase Auth Redirect URLs에 고정 Preview 주소 또는 허용된 Vercel wildcard 등록
- 관리자 권한이 없는 Preview 전용 일반 테스트 계정 준비
- 고정 Preview에서 시각·상호작용·게임 흐름 확인
- merge, destructive migration, 권한·인프라 변경처럼 명시적 확인이 필요한 작업 승인
- Codex가 접근할 수 없는 Dashboard 설정이나 비밀값 입력

사용자는 일반 기능 검증을 위해 로컬 앱이나 로컬 DB를 실행할 필요가 없다. 파괴적 스키마 변경을 재현해야 할 때만 로컬 Supabase를 일회성 검증 도구로 사용할 수 있다.

## 환경

- 환경은 `local`, `preview`, `production`으로 구분한다.
- 초기에는 Supabase 프로젝트와 DB를 하나만 사용한다.
- Preview와 Production은 같은 Supabase DB를 사용한다.
- Preview 검증에는 관리자 권한이 없는 일반 테스트 사용자를 사용하고, Preview 사용자만을 위한 조건 분기를 실코드에 추가하지 않는다.
- 일반 게임 데이터는 기존 사용자 소유권과 RLS로 격리한다.
- 새 테이블·nullable 컬럼·새 함수처럼 기존 Production과 호환되는 확장 변경만 Preview 검증 전에 원격 적용한다.
- 기존 RPC 계약을 깨는 변경은 기존 함수를 교체하지 않고 `*_v2` 같은 새 함수로 추가한다. Production 전환 후에도 구 함수는 즉시 삭제하지 않는다.
- 컬럼·함수 삭제, 대규모 데이터 변환, 권한·인프라 변경은 별도 확인과 후속 정리 단계로 처리한다.
- Supabase 프로젝트를 환경별로 나누는 것은 비용과 운영 필요성이 생겼을 때 검토한다.

## 릴리스와 패치노트

- 버전은 `MAJOR.MINOR.PATCH` 형식을 따른다.
- 버전의 기준값은 `app/package.json`의 `version`이다.
- 클라이언트 업데이트 감지의 배포 기준은 각 Vercel 배포물의 `version.json`이다. DB 패치노트를 클라이언트 버전 기준으로 사용하지 않는다.
- 기능 구현 단계에서는 앱 버전을 올리지 않는다.
- 기능 구현 단계에서는 `app/public/version.json`을 변경하지 않는다.
- 기능 구현 단계에서는 패치노트 migration을 만들거나 원격 DB에 적용하지 않는다.
- 버전 변경, `version.json` 갱신, 패치노트 migration 작성은 머지 단계에서 사용자 확인 후 처리한다.
- 패치노트 migration은 PR에 포함하되 Production 배포 성공 전에는 원격 DB에 적용하거나 공개하지 않는다.
- 작은 수정과 버그 수정은 `PATCH`를 올린다.
- 기능 단위 변경은 `MINOR`를 올린다.
- 호환성을 크게 깨는 변경이나 정식 공개 기준이 생기면 `MAJOR` 변경을 검토한다.
- 사용자 공개 변경은 기능 구현과 같은 릴리스 버전을 사용한다. 패치노트만을 위한 독립 버전은 만들지 않는다.

### 릴리스 파일

- 새 릴리스 PR은 아래 파일을 함께 변경한다.
  - `app/package.json`
  - `app/package-lock.json`
  - `app/public/version.json`
  - 새 `supabase/migrations/*_add_*_patch_note.sql`
- 패치노트 migration의 `patch_notes.version`은 `app/package.json.version`과 같아야 한다.
- `app/public/version.json`의 `latest`는 `app/package.json.version`과 같아야 한다.
- `minimum`은 기존 클라이언트를 강제로 새로고침해야 할 때만 `latest`와 같은 버전으로 올린다. 일반적인 호환 기능 추가에서는 기존값을 유지한다.
- 하나의 PR에 여러 기능이 있어도 사용자 공개 버전은 하나만 사용한다.

### 패치노트 문구

- 패치노트는 사용자에게 보이는 변화만 기록한다.
- 내부 구현 변경은 사용자가 체감하는 변화가 있을 때만 적는다.
- 문장은 짧고 기능적으로 쓴다.
- `tower://` 테마를 약하게 반영하되 과한 농담이나 장황한 설명은 피한다.
- 각 버전은 1~3개 항목으로 시작하고, 필요할 때만 늘린다.
- `patch_notes`에는 버전·출시일·제목을, `patch_note_items`에는 사용자 공개 항목을 기록한다.

### 릴리스 검증

- `npm run build`를 실행한다.
- 적용 후 `npm run db:list`로 로컬과 원격 마이그레이션 이력이 일치하는지 확인한다.
- Preview에서 `/version.json`이 `app/package.json.version`과 같은 `latest`를 반환하는지 확인한 뒤 merge한다.
- `main` merge 후 Vercel Production 배포 성공을 기다린다.
- Production의 `/`, 인증 경로, `/version.json`을 확인한다.
- Production 검증이 끝난 뒤 패치노트 migration을 원격 DB에 적용하고 공개 상태를 확인한다.
- 배포가 실패하면 패치노트를 공개하지 않고 기존 Production을 유지한 채 수정하거나 롤백한다.

## Vercel 배포

- Vercel 프로젝트의 Root Directory는 `app`으로 둔다.
- Build Command는 `npm run build`로 둔다.
- Output Directory는 `dist`로 둔다.
- SPA 직접 접근과 새로고침을 위해 `app/vercel.json`의 rewrite를 유지한다.
- Vercel Git Integration에서 `preview` 브랜치의 최신 배포를 가리키는 branch-specific URL을 고정 검증 주소로 사용한다.
- 도메인을 보유한 경우 선택적으로 Preview 전용 도메인을 `preview` Git 브랜치에 연결할 수 있다.
- 고정 Preview URL에서 `/`, `/reset-password`, `/version.json`을 확인한 뒤 merge한다.
- Preview 화면에는 현재 환경과 커밋을 식별할 수 있는 표시를 두되, 환경별 게임 동작 분기는 만들지 않는다.

## Supabase Auth Redirect

- 비밀번호 재설정 redirect 경로는 `/reset-password`를 사용한다.
- Supabase Auth Redirect URLs에는 local, preview, production URL을 등록한다.
- 로컬 개발 주소 예: `http://127.0.0.1:5173/**`.
- Vercel preview 테스트가 필요하면 preview URL 또는 `https://*.vercel.app/**`를 등록한다.
- production 도메인을 연결하면 `https://도메인/**`과 필요한 `www` 도메인을 함께 등록한다.

## 인증 상태

- 인증 화면은 명시적인 상태 모델을 따른다.
- 예: `checking`, `signed-out`, `profile-required`, `signed-in`, `reset-request`, `reset-update`.
- 로그인, 회원가입, 비밀번호 재설정, 프로필 생성 흐름을 한 상태에 섞지 않는다.

## 마이그레이션

- 마이그레이션 번호를 재사용하지 않는다.
- 이미 원격에 적용된 migration은 수정하지 않는다.
- 변경은 새 migration으로 추가한다.
- 원격 migration history와 로컬 파일 목록이 맞는지 확인한다.
- 기존 설정이나 데이터 구조를 크게 바꾸는 migration은 서버 점검 작업으로 취급한다.
- destructive migration은 별도 확인 후 진행한다.

## 서버 권위

- 클라이언트는 입력과 화면 표시를 담당한다.
- 전투 결과, 보상, 재화, 인벤토리 변경, 랭킹 기록은 서버가 확정한다.
- 서버 권위 로직은 필요한 시점에 Supabase Edge Functions로 추가한다.
